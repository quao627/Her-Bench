陪看双引擎：live agent × codex

gpt-live 负责说话，codex 负责查证，中间是一次 HTTP tool call。

Part 1

核心 loop

浏览器给 gpt-live 两路输入：直播原声和画面帧。要不要开口、要不要查证由它自己判断， 需要查的时候发一个 HTTP 请求给本地的 codex 后端。

Part 2

主要 API

查看器对 agent 的全部要求就是这三个 HTTP 端点，换别的后端实现也能接。

端点谁触发强制？内容形态
/answer 视频经过锚点，POST 整个任务包 直接触发 3-6 句给浏览器 TTS 念，纯情绪的时刻一两句
/lookup gpt-live 调 lookup_game_info must_cite / tool_fit 题强制 不限长度，gpt-live 自己提炼成语音
/research 播放中每 15 秒自己看一眼画面 不强制 判断值得才产出，直接喂给 gpt-live

回答最后单独一行 SOURCES: 是约定格式，服务端用它抽出 citations，判分时看 must_cite 的题有没有真的引用来源。

Part 3

核心设计

一 · 自己决定什么时候开口

Realtime API 只在两种情况出声：显式发 response.create，或者 VAD 听到有人说话。 画面帧只进上下文、不带 response.create，所以光看画面它永远不会自己开口。 要让时机真的由它决定，靠两件事配合。

后台持续喂料。/research 查到东西立刻塞进它的上下文， session instructions 里讲清楚这是先放它手上的储备，不用马上说。 定期自己判断。纯文本响应用户听不到，所以判断「不说」是真的安静， 不会冒出一句「我觉得没什么好说的」。

这个模式下 proactive 题的锚点不再催它说话，退化成评分窗口： 只记录它有没有在 response_window_sec 内自己开口。

二 · proactive 带一条时间线

值不值得开口的依据是时间性的：卡了多久、刚完成了什么。单张锚点帧承载不了， 比如通关那一帧是角色在云里下坠，跟掉出地图的画面几乎一样。

HTTP 模式经过锚点时视频已经 pause，回溯 seek 抓帧再复位即可，不用改播放逻辑。 落点是此刻的处境，中间某一帧闪过的孤立事件已经过去了，不该转头去说它。

三 · 强制查证

现场对话式模型几乎不会承认自己不确定，很擅长把没查过的东西说得像查过。 所以 must_cite 或 tool_fit 为真的题， 用 per-response tool_choice 覆盖，必须走一次 /lookup，判分时再看 citations 里有没有东西。

四 · 资料按进度挑

资料整篇拼进 prompt，所以资料一多每道题都要付这份成本。 resources 常驻，chapter_resources 按 anchor_sec 取当前和下一段。预取下一段是有意的：老玩家本来就知道接下来会发生什么， 防剧透约束的是输出。区间按哪道题需要哪篇倒推，不必照搬章节边界。 Stanley Parable 8 篇共 77KB，这样挑之后每次请求落在 13-26KB。

五 · codex 会话续接

每次都开新的 codex exec 的话，五分钟前查过的东西下一次用不上， 只能从头再搜。改成 resume <thread_id> 接着上一轮，每个 container 两条 thread。

thread谁在用为什么分开
fg /answer + /lookup 有人在等结果
bg /research 同一 thread 只能串行 resume。合成一条的话，前台查证会排在 20 秒的后台研究后面
