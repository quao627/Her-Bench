Diagram · Her-Bench

陪看双引擎：live agent × codex

gpt-live 管嘴（实时语音、听得懂现场），codex 管脑（深度查证、能读资料能搜网）—— 中间靠一次 HTTP tool call 打通。

Part 1

总体架构

浏览器同时喂两路信号给 gpt-live：直播原声（WebAudio 图混音，不开麦克风） 和画面帧（每 5 秒一张）。gpt-live 自己决定要不要开口、要不要查证；一旦要查， 就是一次 HTTP 请求打到本地的 codex 后端。

Part 2

三条请求路径，各管各的

同一个 codex 后端，但被三种不同场景触发，触发条件和是否强制都不一样。

端点谁触发强制？内容形态
/answer HTTP 模式：视频经过锚点自动 POST 整个任务包 直接触发 3-6 句，直接给浏览器 TTS 念
/lookup gpt-live 调 lookup_game_info 工具 must_cite/tool_fit 题强制 不限长度，gpt-live 自己提炼成语音
/research 播放中每 15 秒，agent 自己看一眼当前帧 被动观察，不强制 NOTEWORTHY 才产出，存成「研究笔记」

must_cite / tool_fit 为真的题，用 Realtime API 的 per-response tool_choice 强制覆盖，不是靠 gpt-live 自己判断「够不够确定」—— 现场对话式模型几乎不会主动承认不确定，所以这条规则做成硬性的。

Part 3

自主预研闭环

不是「提前把题目原文发过去查」（那是偷看未来），而是 agent 只从自己看到的画面出发， 自己决定查什么——查到的东西存成笔记，供之后真被问到时自愿参考，不是必须用。

Part 4

一个真实的坑：请求排队

「live agent 说得少、没用」的根因不是提示词，是并发——单线程 server 让自主预研和真提问抢同一个队列。

Part 5

第二个坑：一张帧判断不了「该不该开口」

proactive 考的是开口时机，但值不值得开口的依据全是时间性的——卡了多久、刚完成了什么。 而 HTTP 通道只发一张锚点帧。截帧核对之后发现，这些帧里根本没有判断所需的信息。

锚点那一帧画面上实际有什么为什么判断不了
hff-p1-t18
Water 关通关		 小人在云雾中下坠 Human Fall Flat 没有通关结算画面。这一帧跟「掉出地图」几乎无法区分——而掉出地图正是同一容器里另一道题考的事
stanleyparable-e01-t09
Beat the Game		 阳光小路 + 一句旁白字幕 成就弹窗要到 10 秒后才出现，不在自己的锚点帧里
slendytubbies-e01-t05
只差 2 个被抓		 已经回到主菜单 看不出他撑了 19 分钟、只差 2 个就通关
hff-p1-t09
吊机卡关 10 分钟		 玩家站在吊机前 看不出「已经卡了 10 分钟」，跟正常操作长得一样

症状分两种，同一个根因：画面平淡时模型输出 SILENT（该庆祝的时刻沉默了）； 画面里有点地形时它就脑补成卡关、顺势灌一段攻略（该说「恭喜」的时候给了五句教学）。 模型没做错——是我们只给了一张图，却问了一个只有时间轴才能回答的问题。

改之后 · 附一条时间线

还有一个副产品：hff-p1-t18 的锚点本身就偏早了一拍。 它定在下坠瞬间，而「过关了」这件事只能靠场景切换看出来——锚点往后挪 14 秒到新场景可见处， 这道题才真正变得可答。context_window_sec 只能看锚点之前， 所以锚点必须落在证据已经出现的那一刻，不能落在证据即将出现的前一刻。
