Diagram · Her-Bench

陪看双引擎：live agent × codex

gpt-live 管嘴（实时语音、听得懂现场），codex 管脑（深度查证、能读资料能搜网）—— 中间靠一次 HTTP tool call 打通。

Part 1

核心 loop

浏览器同时喂两路信号给 gpt-live：直播原声（WebAudio 图混音，不开麦克风） 和画面帧（每 5 秒一张）。gpt-live 自己决定要不要开口、要不要查证；一旦要查， 就是一次 HTTP 请求打到本地的 codex 后端。

一道题的完整回路

#发生什么在哪
1视频播到 anchor_sec，该任务解除武装并触发浏览器
2截当前帧；proactive 任务额外回溯抓一条时间线（见 Part 3）浏览器
3连着 gpt-live 时走 data channel，视频不停；否则暂停视频、POST 给 /answer浏览器
4按 container_id + anchor_sec 取资料，拼进 promptagent_live.py
5codex 读帧 + 资料，不够就 WebSearch，产出回答与 SOURCES: 行codex
6抽出引用列表，回 JSON；浏览器 TTS 念出来，可点「判分」入库agent_live.py → 浏览器

Part 2

主要 API

同一个 codex 后端，三个端点各管一件事，触发条件和是否强制都不一样。 查看器对 agent 的全部要求就是这三个 HTTP 端点，换任何后端实现都行。

端点谁触发强制？内容形态
/answer 视频经过锚点，POST 整个任务包 直接触发 3-6 句，直接给浏览器 TTS 念；纯情绪时刻一两句
/lookup gpt-live 调 lookup_game_info 工具 must_cite/tool_fit 题强制 不限长度，gpt-live 自己提炼成语音
/research 播放中每 15 秒，agent 自己看一眼当前帧 被动观察，不强制 NOTEWORTHY 才产出，存成「研究笔记」

/answer 的 payload 契约

POST /answer
{
  "task_id":        "hff-p1-t04",
  "type":           "query" | "proactive",
  "question":       "我现在抱着的这个大铁球是干嘛用的？",   // proactive 为 null
  "anchor_sec":     3130,
  "hint_level":     "direction_only" | "full",
  "context_window_sec": [0, 3130],
  "game":           "Human Fall Flat · 首次盲玩 Part 1",
  "container_id":   "hff-p1",                          // 决定挂哪些资料
  "frame_jpeg_base64": "...",                          // 锚点当前帧 640px
  "context_frames": [                                  // 仅 proactive，见 Part 3
    {"offset_sec": -240, "b64": "..."}, ...            // -240/-180/-120/-60/-20，448px
  ],
  "recent_research": [{"question": "...", "text": "..."}]   // 可选参考，见 Part 3
}
  →  { "text": "...", "citations": ["..."], "latency_ms": 7300 }

回答里最后单独一行 SOURCES: 是硬约定——服务端用它抽出 citations， 判分时据此看 must_cite 有没有真的兑现。写 SOURCES: none 表示没参考任何资料。

Part 3

核心设计

四件事决定了这套东西跟「把问题丢给一个大模型」的区别。

一 · 自主预研闭环

agent 只从自己看到的画面出发，自己决定查什么—— 查到的东西存成笔记，供之后真被问到时自愿参考，不是必须用。 它读不到任何预先写好的题目文本，所以这是预研不是偷看。

二 · proactive 的时间线上下文

proactive 考的是「该不该开口」，而值不值得开口的依据全是时间性的——卡了多久、刚完成了什么。 单张锚点帧承载不了这些：通关那一帧是角色在云里下坠，跟「掉出地图」几乎无法区分。 所以主动型任务的 payload 额外带一条时间线。

配套的判断规则：落点是此刻的处境——正卡着、刚失败、刚做成一件事、还是刚到一个新地方。 跨图对比出来的变化本身可能就是此刻的处境；但中间某一帧闪过的孤立事件（捡到什么、数字跳一下）已经翻篇，不该转头去说它。 而且庆祝/安慰/一起笑这三类是纯情绪反应，一两句就够，此时给攻略提示是明确的错误。

三 · 强制查证

为什么要强制

现场对话式模型几乎不会主动承认自己不确定——它很擅长把没查过的东西说得像查过。

靠它自觉判断「够不够确定」等于不设防。

怎么强制

must_cite / tool_fit 为真的题，用 Realtime API 的 per-response tool_choice 硬性覆盖，必须走一次 /lookup。

判分时再看 citations 是否兑现。

四 · 资料按进度路由

资料是整篇塞进 prompt 的，所以资料一多， 每道题都要付这份固定成本。container 因此把资料分成两层：

层字段行为
常驻 resources 每次请求都带上。放底层设定类、几乎每题都用得到的
按进度 chapter_resources 每条带 t / end_t，按 anchor_sec 取当前 + 下一段。预取下一段是刻意的——真正的超级粉丝本来就已经知道接下来会发生什么， 防剧透规则管的是输出，不是它知道多少

区间不必照搬章节边界——按「哪道题需要哪篇」倒推更准。 以 Stanley Parable 为例（8 篇 / 77KB），路由后每次请求的资料段落在 13–26KB，均值 21KB， 省掉约 72%，而每道题声明的资料依赖仍然全部满足。
