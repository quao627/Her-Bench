陪看双引擎：Realtime 与 codex

Realtime 常驻在浏览器这端，听得到、看得到、负责说话；codex 负责查证，中间是一次 HTTP 调用。

Part 1

核心 loop

浏览器给 Realtime 两路连续输入：直播原声和画面帧，两路都只进上下文，不触发任何输出。 要不要开口、要不要查证由它自己在自检里决定，需要查的时候发一个 HTTP 请求给本地的 codex 后端。

它开口只有两个来路：自检判定要说，或者主播问出声。定时喂进来的画面、备料查回来的内容， 都只是让它手上多一些材料。

Part 2

主要 API

查看器对后端的全部要求就是这几个 HTTP 端点，换别的后端实现也能接。

端点谁触发有人等吗内容形态
/answer 视频经过锚点，POST 整个任务包 有 3-6 句给浏览器 TTS 念，纯情绪的时刻一两句
/lookup Realtime 调 lookup_game_info；自检提的查证也走这里，只多一个 background 标志 主播问的有
自检提的没有		 不限长度，Realtime 自己提炼成语音
/research 备料定时器，每 T_brief 把最近 N_brief 帧交过去 没有 只塞进上下文当储备，不触发自检
/cancel 语音检测一响就发，主播问话优先 — 杀掉那条 codex 子进程，会话一并作废
/progress 前端轮询 — codex 事件流里读到的进度，供界面回显 
POST /lookup
{
  "query": "货叉车怎么升起来",          // 问题始终由前台 agent 提
  "container_id": "hff-p1",
  "current_sec": 3130,                  // 决定挂哪一段资料
  "background": true,                   // true=自检提的，没人等；false=主播问的
  "frames": [{"offset_sec": -20, "b64": "..."}, ...],
  "call_id": "c-8f2a"                   // /progress 用它取进度
}
  →  { "text": "...", "citations": ["..."], "latency_ms": 16400 }

回答最后单独一行 SOURCES: 是约定格式，服务端用它抽出 citations，判分时看 must_cite 的题有没有真的引用来源。

Realtime 那一侧的两个工具

一个给它主动查资料用，一个专门用来把自检的结论交回来。

lookup_game_info(query)          // 主播问到具体事实时它自己调，转发到 /lookup

decide(speak, say, lookup, need_frame)   // 自检专用，一次判断出两个结论
  speak      : boolean   // 此刻要不要开口
  say        : string    // 要说的话的要点，不说就传空
  lookup     : string    // 想让后台查的问题，不查就传空
  need_frame : boolean   // 这次查证要不要附画面

Part 3

核心设计

一 · 只有一个决策点

输入是流式的，但 Realtime API 不会自发说话：往对话里塞 item 不触发生成， 只有显式发 response.create、或者语音检测判定人说完了才会。 所以要定期让它自己判断一次，开口和查证在同一次判断里决定。 结论用一次强制的 decide 工具调用交回来，参数由 API 按 schema 校验。

二 · 主播问话优先

语音检测是最早的信号，比它自己调工具早十几秒。一响就把后台正在跑的那条掐掉： 浏览器 abort 请求，同时打一个 /cancel，后端把 codex 子进程杀掉。 只 abort 请求不够，进程还在占着 CPU 和那条会话，前台的查证只会更慢。 被杀的会话一并作废，下次从干净的会话重开。这段时间也不自检、不备料。

三 · 喂料和开口分开

备料通道由定时器驱动，每 T_brief 把最近 N_brief 帧交给 codex， 让它自己从画面里想一个问题去查。查回来的只塞进上下文，不触发自检； 只有 agent 自己在自检里提出的查证，回来时才会触发下一次。喂料可以定时做， 什么时候说话必须留在 agent 手里。这条通道可以整条关掉，用来对照它完全自力更生时的表现。

备料只备方向：整套通关步骤摆在它手上很容易提前说出去，所以备的是「这是什么、怎么回事」， 也不写当前进度之后的关卡和剧情。

另有一条地板保护：连续几次自检都没提出要查的东西，下一次会要求它必须提一个。 要求的是提问，问题仍由它自己出。

四 · 判断要看一段时间线

值不值得开口，取决于这段时间发生了什么：卡了多久、刚完成了什么。单张画面看不出这些， 比如通关那一帧是角色在云里下坠，跟掉出地图的画面几乎一样。 所以浏览器一直留着最近五分钟的帧，取用时近处密、远处稀。

刚做成一件事、刚摔下去、还是原地打转，都发生在最近十几秒里，那一段必须密； 再往前只是用来看这段时间有没有挪窝。

锚点触发的题走的是另一条路：那时视频已经暂停，回溯 seek 抓帧再复位即可，不用改播放逻辑。 要回应的是此刻的处境；中间某一帧闪过的孤立事件已经过去，不必再提。

五 · 强制查证

对话式模型很少表示自己不确定，容易把没有查过的内容说得像查过一样。 所以 must_cite 或 tool_fit 为真的题， 用 per-response tool_choice 覆盖，必须走一次 /lookup，判分时再看 citations 里有没有内容。

六 · 资料按进度挑

资料整篇拼进 prompt，所以资料一多每道题都要付这份成本。 resources 常驻，chapter_resources 按 anchor_sec 取当前和下一段。同时取下一段，是因为防剧透约束的是输出内容， 而不是 agent 能看到多少；有经验的玩家本来也知道后面会发生什么。区间按哪道题需要哪篇倒推，不必照搬章节边界。 Stanley Parable 8 篇共 77KB，这样挑之后每次请求落在 13-26KB。

七 · codex 会话续接

每次都开新的 codex exec 的话，五分钟前查过的东西下一次用不上， 只能从头再搜。改成 resume <thread_id> 接着上一轮，每个 container 两条会话。

会话谁在用截止线为什么分开
fg 主播问出声的查证、锚点题 40s（锚点题 120s） 有人在等结果
bg 自检提的查证、备料 90s 同一条会话只能串行 resume。合成一条的话，有人等的查证会排在后台那条后面

codex 自己不会因为查得太久停手，只能从外面卡截止线，超时返回一句能直接用的话， 而不是让前台干等。前端另有一条稍宽的截止线，否则后端一挂，「正在查」的标志就永远落不下来。
