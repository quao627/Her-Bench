Diagram · Her-Bench

陪看双引擎：live agent × codex

gpt-live 负责说话，听得懂现场也能实时回应；codex 负责查证，能读资料也能搜网。 两者之间是一次 HTTP tool call。

Part 1

核心 loop

浏览器给 gpt-live 两路输入：直播原声（WebAudio 混音，不开麦克风）和画面帧（每 5 秒一张）。 要不要开口、要不要查证由 gpt-live 自己判断。需要查的时候，它发一个 HTTP 请求给本地的 codex 后端。

一道题的完整回路

#发生什么在哪
1视频播到 anchor_sec，任务触发浏览器
2截当前帧。proactive 任务额外回溯抓一条时间线，见 Part 3浏览器
3连着 gpt-live 时走 data channel，视频不停；否则暂停视频，POST 给 /answer浏览器
4按 container_id 和 anchor_sec 挑资料，拼进 promptagent_live.py
5codex 读帧和资料，不够就 WebSearch，产出回答和 SOURCES: 行codex
6抽出引用列表回 JSON，浏览器 TTS 念出来，可以点判分入库agent_live.py → 浏览器

Part 2

主要 API

同一个 codex 后端，三个端点各管一件事，触发条件和是否强制都不一样。 查看器对 agent 的全部要求就是这三个 HTTP 端点，换别的后端实现也能接。

端点谁触发强制？内容形态
/answer 视频经过锚点，POST 整个任务包 直接触发 3-6 句，直接给浏览器 TTS 念。纯情绪的时刻一两句
/lookup gpt-live 调 lookup_game_info 工具 must_cite/tool_fit 题强制 不限长度，gpt-live 自己提炼成语音
/research 播放中每 15 秒，agent 自己看一眼当前帧 被动观察，不强制 判断为 NOTEWORTHY 才产出，存成研究笔记

/answer 的 payload

POST /answer
{
  "task_id":        "hff-p1-t04",
  "type":           "query" | "proactive",
  "question":       "我现在抱着的这个大铁球是干嘛用的？",   // proactive 为 null
  "anchor_sec":     3130,
  "hint_level":     "direction_only" | "full",
  "context_window_sec": [0, 3130],
  "game":           "Human Fall Flat · 首次盲玩 Part 1",
  "container_id":   "hff-p1",                          // 决定挂哪些资料
  "frame_jpeg_base64": "...",                          // 锚点当前帧 640px
  "context_frames": [                                  // 只有 proactive 有，见 Part 3
    {"offset_sec": -240, "b64": "..."}, ...            // -240/-180/-120/-60/-20，448px
  ],
  "recent_research": [{"question": "...", "text": "..."}]   // 可选参考，见 Part 3
}
  →  { "text": "...", "citations": ["..."], "latency_ms": 7300 }

回答最后单独一行 SOURCES: 是约定好的格式。服务端用它抽出 citations， 判分时据此看 must_cite 的题有没有真的引用来源。没参考任何资料就写 SOURCES: none。

Part 3

核心设计

一 · 自己决定什么时候开口

Realtime API 只有两种情况会让模型出声：显式发 response.create，或者 VAD 听到有人说话。每 5 秒喂进去的画面帧只进上下文、不带 response.create，所以光靠画面它永远不会自己开口。要让开口时机真的由它决定，需要两件事配合。

后台持续喂料。/research 查到值得留意的东西，立刻塞进它的对话上下文，标成 [后台资料·时间]， 同样不带 response.create。session instructions 里一开始就讲清楚这套安排： 这些是先放你手上的储备，不用马上说，等他真需要或者问起来再用。

定期自己判断。每 25 秒（可调）让它先出一个 纯文本响应做决定，用户听不到；决定要说才发第二个语音响应。 文本响应用 output_modalities: ["text"] 限定，所以判断「不说」的时候是真的安静， 不会冒出一句「我觉得没什么好说的」。

二 · proactive 的时间线

proactive 考的是该不该开口，而判断依据是时间性的：卡了多久、刚完成了什么。 单张锚点帧承载不了这些。比如通关那一帧是角色在云里下坠，跟掉出地图的画面几乎一样。 所以 proactive 的 payload 额外带一条时间线。

配套的判断规则：落点是此刻的处境，正卡着、刚失败、刚做成一件事、还是刚到一个新地方。 跨图对比出来的变化本身可能就是此刻的处境；但中间某一帧闪过的孤立事件（捡到什么、数字跳一下）已经过去了，不该转头去说它。 庆祝、安慰、一起笑这三类是纯情绪反应，一两句就够，这时候给攻略提示是错的。

三 · 强制查证

为什么要强制

现场对话式模型几乎不会主动承认自己不确定，很擅长把没查过的东西说得像查过。

让它自己判断够不够确定，等于没有约束。

怎么强制

must_cite 或 tool_fit 为真的题，用 Realtime API 的 per-response tool_choice 覆盖，必须走一次 /lookup。

判分时再看 citations 里有没有东西。

四 · 资料按进度挑

资料是整篇拼进 prompt 的，所以资料一多，每道题都要付这份固定成本。 container 因此把资料分成两层。

层字段行为
常驻 resources 每次请求都带上。放底层设定这类几乎每题都用得到的
按进度 chapter_resources 每条带 t 和 end_t，按 anchor_sec 取当前和下一段。预取下一段是有意的：真正的老玩家本来就知道接下来会发生什么， 防剧透规则约束的是输出，不是它知道多少

区间不必照搬章节边界，按哪道题需要哪篇倒推更准。 Stanley Parable 有 8 篇共 77KB，这样挑之后每次请求的资料落在 13-26KB，均值 21KB， 省掉约 72%，每道题声明的资料依赖仍然都能拿到。

五 · codex 会话续接

每次调用如果都是全新的 codex exec， 五分钟前查过的东西下一次完全用不上，只能从头再搜一遍。改成用 codex exec resume <thread_id> 接着上一轮，每个 container 维持自己的 thread。

thread谁在用为什么分开
fg /answer + /lookup 有人在等结果。多次查证之间能接上，不用重复搜
bg /research 没人等，按定时器跑。跟前台分开是因为同一个 thread 只能串行 resume，合在一起的话一次前台查证会排在 20 秒的后台研究后面

首次调用带 --json，从 thread.started 事件里取 thread_id 存下来； 之后都走 resume。每个 thread 各自一把锁，因为并发 resume 同一个 thread 会让两个 codex 进程写同一份会话文件。
