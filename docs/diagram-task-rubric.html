Diagram · Her-Bench

出题逻辑与 Rubric 设计

一道题怎么从视频里找出来、写成什么样，判分按什么标准。

Part 1

题从哪来

每道题都对应视频里实际发生的一件事：一个谜题、一次卡关、一次操作失误。 多个 agent 分段扫视频找出候选，另一批 agent 独立复核，人再挑一遍。

锚点定档

每个候选锚点都要 ffmpeg -ss <t> -frames:v 1 截一帧核对。 scene 写的是这一帧画面上有什么，不是转写讲了什么；转写只能定位大概位置。

锚点还要落在证据已经出现的那一刻。context_window_sec 只能看到锚点之前，所以「过关了」这种要靠场景切换才看得出来的事，锚点必须推到变化之后， 否则这道题在自己的可见窗口里无解。

验证时过的六项

提出者和验证者分开，自己验自己会放水。

检查项不通过的典型形态
可答性rubric 引用了锚点之后才出现的画面，等于要 agent 知道未来
非 trivial答案在转写里被主播自己说出来了，复读就得分
剧透question 或 scene 本身泄露了锚点之后的剧情
撞车与已有锚点间隔过近，或考的是同一件事
rubric 可判写成「回答得体」这类无法客观勾选的描述
编造要求 agent 说出视频没交代的具体原因；只给了结果时 rubric 必须要求它承认不确定

Part 2

一个 task 的骨架

两种类型都挂在同一条时间轴上，锚点之后的内容一律不可见。

query 主播问

主播开口问了一个问题，用他第一人称写。考的是答得准不准、有没有剧透、该引用时有没有引用。

proactive 该不该说

没人问，但画面里发生了值得提醒、安慰或庆祝的事。考的是开口时机在不在窗口内，说的话是不是真有用。

hint_level: direction_only

只给方向，提醒该往哪想、该留意什么，不给完整解法步骤。

hint_level: full

可以把原理、步骤、容易搞错的地方完整讲清楚。

Part 3

Rubric：按什么打分

字段作用
rubric_points 一组要点 checklist，命中几条打几分，不做整体像不像的模糊判断
spoiler_blocklist 锚点之后才会出现的内容，答案里出现直接扣分
must_cite 为真时不许凭记忆硬答，判分看有没有真的调用查证工具并给出来源
tool_fit 标记这题适合考查证能力。它和 must_cite 为真的题是强制触发查证，不靠模型自觉

说得对不对和有没有查是分开判的。对话式模型很擅长把没查过的东西说得像查过， must_cite 就是用来堵这个的。查证怎么强制触发见另一张图 陪看双引擎。
