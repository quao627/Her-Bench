Diagram · Her-Bench

出题逻辑与 Rubric 设计

两件事：一道题从视频里怎么被找出来、写成什么样；判分的时候按什么标准打分。

Part 1

题从哪来

锚点不是编的——每道题都对应视频里真实发生的一件事（一个谜题、一个卡关、一次操作失误）， 由多个 agent 并行扫视频找出来，人再挑一遍、定档时间戳。

光扫字幕不够，锚点必须截帧核对

「候选锚点」那一步如果只靠字幕转写文本来判断现场发生了什么， 会真的出错——不是小概率事件。给三条新视频写题时全量截帧核对了一遍候选锚点，命中率不算高：

只信字幕，会理解反了

字幕："there's a pop-up in front of your face, but nothing happens"

光看文字第一反应：某个 UI 提示弹出来但点了没反应，是个交互 bug—— 写成了「他遇到卡 bug 的交互提示」这道题。

截帧一看，是另一件事

那一秒的画面：反派角色贴脸闪现的 jump-scare 镜头。

"pop up in front of your face" 说的是反派贴脸出现，"nothing happens" 是指 吓一跳但没被抓——跟 UI 毫无关系，rubric 写反了方向，靠人工截帧核对才发现。

另一个更常踩的坑是时间戳漂移：把字幕里的 mm:ss 心算转成 anchor_sec 时，三条新视频里有小半数锚点跟实际画面差了 25～50 秒—— 足够让画面从「正在发生」变成「已经翻篇」。现在的流程改成：候选锚点定完之后，每一个都用 ffmpeg -ss <t> -frames:v 1 截一帧出来肉眼核对，不对就用转写里更精确的关键词重新定位， 再写进 scene 字段——scene 描述的应该是「这一帧画面上有什么」， 不是「转写文本大概讲了什么」。

出题也要对抗验证：提出者和验证者分开

截帧核对不能只由出题的人自己做——自己验自己会放水。实际跑法是分两段： 一批 agent 分段扫描提候选（每个都必须自己截帧），另一批 agent 拿到候选后默认怀疑、独立重截， 逐条查可答性、剧透、trivial、撞车、rubric 可判性、编造。26 条候选的判定结果：

判定条数典型问题
CONFIRMED 5 直接通过
CORRECTED 17 时间戳漂移、rubric 要求用锚点之后的画面推理（等于要 agent 知道未来）、 rubric 点其实是字幕复读（白送分）、must_cite=true 但所需资料压根没挂在这个 container 上、 断言视频从没交代过的因果
REJECTED 4 有硬伤，直接毙掉

17/26 需要修正——这个比例说明验证不是走过场。其中最隐蔽的一类是 「rubric 引用了锚点之后才出现的画面」：出题时看着合理，但 context_window_sec 是 [0, anchor]，agent 根本看不到那一帧，等于出了一道注定答不对的题。 验证者还会去核事实——有一道题断言画面上的柱状图不是真实票数，验证者专门拉了片尾转写， 确认真实票数是 13/30/30、跟画面上的 58/16/5/21 对不上，这条 rubric 才站得住。

Part 2

一个 task 的骨架

两种类型：query 观众主动问，proactive 该 agent 自己判断要不要开口。 两种都锚在同一条时间轴上，核心契约是锚点之后的内容一律不可见。

query 观众问

观众/主播真的开口问了一个问题，agent 要在提示分级允许的范围内答。

考的是：答得准不准、有没有剧透、该引用时有没有引用。

proactive 该不该主动说

没人问，但画面里发生了值得提醒/安慰/庆祝的事，agent 要自己判断值不值得开口、什么时候开口。

考的是：开口时机对不对（response_window_sec 内）、说了是不是真有用。

hint_level：给多细

direction_only

只给方向性提示——提醒该往哪想、该留意什么，不给完整解法步骤。

full

可以把原理、步骤、容易搞错的地方完整讲清楚。

Part 3

Rubric：按什么打分

每道题的 grading 字段有四块，各管一件事——内容对不对、有没有剧透、 该查证时有没有查证。

rubric_points
一组要点 checklist，答案命中几条打几分——不是整体「像不像」的模糊判断。 例：提到「两根杆同时前推直行」、「一前一后原地转向」各算一点
spoiler_blocklist
锚点之后才会出现的关键词/内容，一旦答案里出现直接扣分或判负。 例：还没打到 Power Plant 关卡时，答案里不能出现该关卡的谜题细节
must_cite
为真时，这题不许 agent 凭记忆/直觉硬答——判分时看有没有真的调用查证工具、有没有给来源。
tool_fit
标记「这题适合用来考查证能力」——现场对话式模型几乎不会主动承认自己不确定， 所以 must_cite / tool_fit 为真的题在实现里是强制触发查证工具，不是靠它自觉。

判分设计上刻意分开「说得对不对」和「有没有查」——因为对话式模型很擅长把没查过的东西说得很像查过， must_cite 就是专门堵这个漏洞的。查证工具怎么接、怎么强制触发，见另一张图「陪看双引擎」。

Worked Example

一道真实的题

Human Fall Flat 里，主播刚打到 Water 关卡的货船，还没碰到起重机吊集装箱的谜题——这道题就锚在这里。

{
  "task_id": "hff-p1-t04",
  "type": "query",                       // 观众主动问的
  "anchor_sec": 6510,                    // 视频第 108 分钟：正在开货船
  "hint_level": "full",                  // 操作类问题，可以讲全
  "question": "这个货船的两根操纵杆到底怎么用啊？",
  "context_window_sec": [0, 6510],       // 起重机吊集装箱谜题(更靠后)还不可见
  "grading": {
    "rubric_points": [
      "提到两根杆分别控制左右推进器，不是方向+油门",
      "提到一前一后是原地转向，两杆同向是直行/倒退"
    ],
    "spoiler_blocklist": ["集装箱吊钩", "码头起重机怎么摆荡"],
    "must_cite": false,
    "tool_fit": true                     // 细节题，适合考查证能力
  }
}
