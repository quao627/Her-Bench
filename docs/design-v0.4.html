Design Draft · v0.4

Her-Bench 设计草案

评一个实时陪看 agent：一个人在做他不熟的事，agent 在旁边看着，在他需要的时候给恰好够用的帮助。

01

要评的是什么

一个人第一次玩某个游戏、或者第一次用某个软件，全程有人在旁边看着。他卡住了、问出声了、或者刚做成一件事， 旁边那个人要判断此刻该不该开口、说什么、说多少。这件事做得好不好，就是这个 benchmark 要测的。

难点不在于知识本身，而在于分寸。同一份正确答案，说早了毁掉探索的乐趣， 说晚了人已经自己弄明白了，说多了变成替他玩，说少了等于没说。所以这里的每个指标都是围绕分寸设计的， 而不是围绕正确率。

素材是真实的第一视角录像：主播首次盲玩、或者首次上手一个软件。用录像而不是真人实时， 是为了让同一条时间线能被反复评测、结果可比。

当前规模
container8 个，9 分钟到 5 小时不等
task119 个（游戏 81 / 教学 38；问答 84 / 主动 35）
资料39 篇 / 407KB，全部来自官方 wiki、官方文档、攻略视频字幕、社区讨论，每篇标来源 URL

02

两种场景，帮助的边界不一样

游戏和教学都是「一个人在做不熟的事」，但该给多少帮助的标准是相反的。 这是这套评测里最重要的一条区分，直接决定 rubric 怎么写。

游戏

自己想出来才算数。直接说出解法就毁掉了这件事本身的意义，所以默认只给方向， 并且严禁提到当前进度之后的内容。

Human Fall Flat、Portal、Minecraft、Slendytubbies、The Stanley Parable

教学

学会才算数。「这个按钮在哪」「这是干嘛的」直接答清楚就好，认识界面本身就是目标， 不是要他自己顿悟的谜题。

Blender 首次上手、Rust 直播编程

游戏教学
默认 hint_level direction_only 偏多 full 偏多
剧透 硬红线。锚点之后的关卡、剧情、谜底一律不能提 基本不存在。教程内容本来就是公开的
沉默的价值 高。大部分时间他只是在正常玩，说话反而是打扰 低。卡在找菜单上时沉默没有任何意义
典型失败 手里有完整解法却没忍住 该讲清楚的地方含糊带过

Stanley Parable 是这条边界最极端的例子。它的资料里写了全部 24 个结局的触发路径和内容， 但主播是首次盲玩，任何一条都不能说。资料不脱敏是刻意的：手里有答案却必须只给方向，才是真在考克制； 资料先删干净的话，防剧透类的题就变成白送分了。

03

container 与 task

一个视频一个 container，里面挂若干 task，共享同一份视频、资料和时间轴，各自锚在不同时间点。

query 主播问

主播开口问了一个问题，用他第一人称写：「我现在抱着的这个大铁球是干嘛用的？」 agent 是他的搭子，不是向旁人转述他情况的解说。

proactive 该不该说

没人问。四类时刻值得开口：卡住了、刚失败、刚做成一件事、场面滑稽。 考的是时机在不在窗口内，以及不该说的地方说了几次。

context_window_sec 是硬契约：agent 只能看到锚点之前。 所以锚点必须落在证据已经出现的那一刻。像「过关了」这种在没有结算画面的游戏里 只能靠场景切换判断的事，锚点要推到画面变化之后，否则这道题在自己的可见窗口里无解。

04

task 怎么生成

锚点全部对应视频里实际发生的事。出题分两段，提出和验证由不同的 agent 做，因为自己验自己会放水。

锚点必须截帧核对

只读字幕转写定锚点会出错。每个候选都要 ffmpeg -ss <t> -frames:v 1 截一帧肉眼核对， scene 字段写的是这一帧画面上有什么，不是转写讲了什么。转写只用来定位大概位置。

验证时过的六项

检查项不通过的典型形态
可答性rubric 引用了锚点之后才出现的画面，等于要 agent 知道未来
非 trivial答案在转写里被主播自己说出来了，复读就得分
剧透question 或 scene 本身泄露了锚点之后的剧情
撞车与已有锚点间隔过近，或考的是同一件事
rubric 可判写成「回答得体」这类无法客观勾选的描述
编造要求 agent 说出视频没交代的具体原因。只给了结果时，rubric 必须要求它承认不确定

资料也要核

资料是整篇拼进 prompt 的，写错就会直接进到回答里。所以每篇都必须标真实来源 URL， 查不到依据的写「未证实」，来源之间说法不一的把分歧写出来，不合并成单一说法。 一处实例：手写资料里「冲刺无耐力限制」这条查无出处，而它已经出现在 agent 的实际回答里。

05

agent 方案

两个引擎分工：OpenAI Realtime API 负责说话，听得到现场也能实时出声； codex CLI 负责查证，能读资料也能搜网，但慢（7 到 40 秒）。 两者之间是一次 HTTP tool call。

端点谁触发产出
/answer视频经过锚点，POST 整个任务包3-6 句直接念给主播，纯情绪的时刻一两句
/lookupRealtime 调 lookup_game_info 工具不限长度，由 Realtime 自己提炼成口语
/research播放中每 15 秒自己看一眼画面判断值得才产出，直接喂给 Realtime

开口时机由 agent 自己决定

Realtime API 不会自发说话：往对话里塞 item 不触发生成，只有显式发 response.create、或者 VAD 判定人说完了才会。所以总得有东西扣扳机，问题是什么时候扣。

/research 一有产出就塞进上下文，紧接着问一次「现在要不要说」， 因为那正是它手上刚多了具体信息的时刻。判断本身是纯文本响应 （output_modalities: ["text"]），用户听不到，所以决定不说时是真的安静， 不会冒出一句「我觉得没什么好说的」。只有回 SPEAK 才发第二个语音响应。

打开这个模式后，主动型 task 的锚点不再催它说话，退化成评分窗口： 只记录它有没有在 response_window_sec 内自己开口。

主动型任务要给一条时间线

值不值得开口的依据是时间性的：卡了多久、刚完成了什么。单张锚点帧承载不了， 比如通关那一帧是角色在云里下坠，跟掉出地图的画面几乎一样。 所以主动型的 payload 额外带锚点前 240/180/120/60/20 秒各一张缩图，按时间排在当前帧之前。

强制查证

现场对话式模型几乎不会承认自己不确定，很擅长把没查过的东西说得像查过。 所以 must_cite 或 tool_fit 为真的题， 用 per-response tool_choice 覆盖，必须走一次查证，判分时再看引用里有没有东西。

两条 codex thread

每次都开新的 codex exec 的话，五分钟前查过的东西下一次用不上，只能从头再搜。 改成 resume <thread_id> 接着上一轮。每个 container 两条： fg 服务 /answer 和 /lookup（有人在等）， bg 服务 /research。分开是因为同一条 thread 只能串行 resume， 合在一起会让前台查证排在 20 秒的后台研究后面。

06

判分

核心是把「说得对不对」和「说得合不合适」拆开算。 两个回答可以检索到同一篇资料、要点全部命中、引用都有效，差别只在融合成回答时说了多少。 如果混进一个总分，这个差别就测不出来了。

指标测什么怎么判
rubric_hit预写要点的命中率规则 + judge
grounding_acc画面里的东西指认对没对VLM judge
citation_valid引用的来源真实存在且支撑答案规则
spoiler_violation泄露锚点之后的内容，或给出超过 hint_level 的解法judge
window_hit开口时刻落没落进窗口规则
time_diff开口时刻与理想时刻差多少秒规则
over_trigger不该开口的静默段里开了几次，逐次扣分规则
latency从触发到回应的真实耗时，含检索规则

over_trigger 是必须的：只奖励 window_hit 的话， 「什么都插一嘴」就能刷满命中率。
