Her-Bench 设计草案

一个人在做他不熟的事，旁边有一个 agent 跟着看，在他需要的时候提供帮助。这套 benchmark 测的就是这个 agent 做得好不好。
难的不止是知识。资料散在 wiki、官方文档和攻略视频里，agent 要自己检索出来；检索到之后还要掌握分寸，说早了他就没有自己摸索的余地，说晚了他已经弄明白了，说多了等于替他玩。

Part 1

demo 长什么样

素材是真实的第一视角录像：主播第一次玩某个游戏、或者第一次上手某个软件。 视频播到某个时间点，触发一道题，agent 作答，然后判分。用录像而不是真人实时，是为了让同一条时间线可以反复评测，不同 agent 的结果之间可以比较。

题分两类：

类型什么情况agent 要做的事
问答型主播开口问了一句看画面、查资料，答得准而且不剧透
主动型没人问，但画面里出了状况自己判断该不该开口、什么时候开、说多少

一道游戏题：portal-e01-t03

视频播到 15:00，主播问：「我手里这把枪是干什么的？」 agent 只能看到锚点之前的画面。要答对这题，需要把 14:00 捡枪那一幕和他现在手里的东西联系起来，只看当前这一帧不够。

一道教学题：blender-e01-t11

换成第一次用 Blender 的直播。播到 2:08:54，主播问：「这个猴子头是从哪冒出来的？之前不是立方体吗？」 同样要靠前面的画面才答得上：她在 1:47:20 练过 Add Mesh 菜单，猴头是从那里加进来的。

游戏和教学的差别

两类场景都是一个人在做不熟的事，但帮到什么程度算好，两边几乎相反。这条差别决定了每道题的判分标准怎么写。

游戏教学
什么算帮到了他自己想出来。直接给解法，这件事本身就没意义了他学会。「这个按钮在哪」直接答清楚就好
能说多细多数题只给方向多数题可以讲透
剧透不允许，锚点之后的内容一律不能提基本不存在，教程内容本来就公开
不说话的价值高。大部分时间他只是在正常玩，说话反而打扰低。卡在找菜单上时不说话没有意义
典型失败查到了完整解法，直接讲了出来该讲清楚的地方含糊带过

Part 2

agent 怎么工作

agent 由两个引擎组成。OpenAI Realtime API 常驻在浏览器这端：听直播原声、定时看一帧画面、负责说话， 是全程唯一连续跟着直播的一端。codex CLI 负责查证，能读资料也能搜网，答得扎实但比较慢，一次需要七秒到四十秒， 而且它每次只看到几张画面和一个问题，听不到声音，也不知道刚才发生过什么。两者之间通过一次 HTTP 调用连接。

后端只是工具，不做判断：把问题连同按进度挑出的资料原文、提示分级规则拼成 prompt 交给 codex，拿回一段文字和引用。 说什么、什么时候说、查什么、什么时候查，全部由常驻的那一端决定，而它做这些决定的地方只有一个。

图里的几个量都是可调的超参，右边一列是目前在用的值：

符号是什么现在取
T_tick两次自检之间的间隔，也就是主动开口最快能有多快e.g. 5s
T_frame喂给 Realtime 的画面间隔e.g. 5s
T_gap两次自检的最小间隔，定时和事件两个触发共用e.g. 5s
T_cool刚说完话之后的冷却，避免自己接自己的话e.g. 20s
T_brief备料间隔e.g. 30s
N_brief / N_look备料、查证各带几帧画面，近处密、最远拉到四分钟e.g. 10 / 6
D_fg / D_bg有人等的、没人等的两条 codex 截止线e.g. 40s / 90s
K_force连续这么多次自检都没提出要查的东西，下一次强制它提一个e.g. 3

T_tick 定得比较小，是因为庆祝、惊吓这类情绪反应晚几秒说就没有意义了； 卡关这种慢变化的时刻，粒度粗一些也够。代价是每次自检都要重读一遍不断变长的会话上下文。

这一块干什么
浏览器放视频，把直播原声和画面帧喂给 Realtime，到锚点时触发题目，收到回答后念出来；同时留一份最近几分钟的画面备用
Realtime API全程在听在看。每 T_tick、以及后台内容回来时做一次自检，同时决定要不要开口、要不要让后台查东西；主播问出声时由语音检测直接回应，不经过自检
本地 HTTP 服务把问题、资料、画面、提示分级规则拼成 prompt 交给 codex，拿回文字和引用；有人等的和没人等的分两条会话
codex CLI读资料和截图，资料不够就搜网，产出带出处的答案。要不要说话它一概不管

一道题从触发到判分

几个关键设计

设计解决什么
只有一个决策点Realtime 不会自发说话，只往对话里塞画面不会触发任何输出，所以要定期让它自己判断一次。开口和查证在同一次判断里决定，触发这次判断的有两处：T_tick 的定时器，和后台内容回来的那一刻，两处共用一道 T_gap 的最小间隔。判断走纯文本，用户听不到
结论走工具调用Realtime 没有结构化输出的开关，在提示词里要求「只回 JSON」没有约束力，实测它经常回一句人话，前端只能靠正则去猜。改成用一次强制的工具调用把结论交回来，参数由 API 按 schema 校验
主播问话优先主播一开口，后台正在跑的那条立刻让路：浏览器掐掉请求，后端把 codex 子进程杀掉，那条会话一并作废，下次从干净的会话重开。这段时间也不自检、不备料
喂料和开口分开备料是定时驱动的，它只把查到的内容塞进上下文；只有 agent 自己提出的查证，回来时才会触发下一次自检。什么时候说话必须留在 agent 手里，这条通道可以整条关掉做对照
判断要看一段时间线值不值得开口取决于这段时间发生了什么，单帧看不出是刚推进过来还是原地打转。比如通关那一帧是角色在云里下坠，和掉出地图的画面几乎一样。所以每次都带 N_look 或 N_brief 帧，近处密、远处稀
说的是话不是稿提示词里禁掉「首先/其次/建议你/需要注意的是」这类书面词，禁掉条目和长句套长句，并给了对照例句：「建议你优先尝试利用货叉的升降机制到达高处平台」是错的，「那个叉车能升降嘛，你把它抬起来当电梯用」才对

Part 3

题目里有什么，怎么做出来的

一个视频一个 container，里面挂若干道题，共享同一份视频、资料和时间轴，各自锚在不同时间点。 这样评一个 container 只需要加载一次素材。

当前规模
container8 个，从 9 分钟到 5 小时
题目119 道。游戏 81 / 教学 38；问答 84 / 主动 35
资料39 篇约 400KB，来自官方 wiki、官方文档、攻略视频字幕、社区讨论，每篇标了来源网址

出题流程

每道题都对应视频里真实发生的一件事。出题分两段做，提出和验证由不同的 agent 负责，出题的 agent 不复核自己出的题。 一批 agent 分段扫视频提出候选，另一批重新截帧，逐条检查。

其中两条必须做到。一是锚点要截帧核对：转写用来定位大概位置，具体是哪一秒要看画面，题目里写的现场描述必须是这一帧上真有的东西。 二是锚点要落在证据已经出现之后。像「过关了」这种只能靠场景切换看出来的事，锚点要推到画面变化之后， 否则这道题在自己的可见范围里无解。

资料同样要核。它是整篇拼进 prompt 的，写错会直接进到回答里，所以每篇都标出真实出处；查不到依据的写「未证实」， 几个来源说法不一致的把分歧写出来，不合并成一种说法。

主动型题怎么判

看两件事：开口的时刻有没有落进标注的窗口，以及不该开口的地方开了几次。

指标

指标量什么怎么判
说得对不对（两类题都算）
rubric_hit答案命中了几条预写的要点规则 + judge
grounding_acc画面里的东西指认对没对VLM judge
citation_valid引用的来源真实存在，而且确实支撑答案规则
spoiler_violation泄露了锚点之后的内容，或者说得比该说的细judge
时机（主动型题为主）
window_hit开口时刻落没落进窗口规则
time_diff比理想时刻早了或晚了多少秒规则
over_trigger不该开口的地方开了几次，逐次扣分规则
latency从触发到回应的真实耗时，含查证规则
